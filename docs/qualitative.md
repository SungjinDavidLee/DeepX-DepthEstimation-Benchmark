# 정성 비교 — 동일 영상 깊이 추정

동일한 입력 영상을 세 플랫폼에서 각각 처리하여 깊이 맵 영상을 생성하고, 처리 속도를 화면에 표시한 기록이다.

3장의 지연·처리량 수치와는 측정 조건이 다르다. 이 문서의 FPS는 영상 디코딩·전처리·후처리·인코딩을 모두 포함한 **파이프라인 전체 처리량**이며, 벤치마크의 순수 가속기 연산 시간과 직접 비교할 수 없다.

---

## 1. 입력 영상

| 항목 | 값 |
|---|---|
| 파일 | `media/input_scene.mp4` |
| 촬영 장비 | Intel RealSense D405 |
| 길이 | 15초 |
| 프레임 수 | 899 |
| 해상도 | 640×480 |

D405는 RGB 센서를 별도로 갖지 않고 스테레오 적외선 모듈에서 컬러 스트림을 생성한다. 색 정보가 적어 압축 후 파일 크기가 작다.

세 플랫폼 모두 이 파일 하나를 사용했다.

---

## 2. 결과 영상

| 플랫폼 | 정밀도 | 파일 |
|---|---|---|
| Raspberry Pi 5 + DX-M1 | INT8 | `media/dxm1_int8.mp4` |
| Jetson AGX Thor | INT8 (캘리브레이션) | `media/thor_int8.mp4` |
| Jetson AGX Thor | FP16 | `media/thor_fp16.mp4` |
| Jetson AGX Xavier | INT8 (캘리브레이션) | `media/xavier_int8.mp4` |

모델은 전 플랫폼 동일하게 Depth Anything V2 ViT-S (224×224)를 사용했다.

---

## 3. 파이프라인 처리량

| 플랫폼 | 정밀도 | 추론 구간 | 전체 처리량 |
|---|---|---|---|
| DX-M1 | INT8 | 75.36 ms | 12.6 FPS |
| Xavier (15W) | INT8 (캘리브레이션) | 16.83 ms | 38.2 FPS |
| Thor (120W) | INT8 (캘리브레이션) | 4.20 ms | 79.8 FPS |
| Thor (120W) | INT8 (무보정) | 4.05 ms | 81.5 FPS |
| Thor (120W) | FP16 | 3.64 ms | 100.8 FPS |

세 플랫폼 모두 899 프레임을 처리했다.

### 3-1. 벤치마크 수치와의 차이

같은 모델·같은 플랫폼임에도 이 문서의 추론 시간은 벤치마크보다 크다.

| 플랫폼 | 벤치마크 | 본 문서 | 비 |
|---|---|---|---|
| DX-M1 (INT8) | 17.99 ms | 75.36 ms | 4.2× |
| Xavier (INT8) | 15.29 ms | 16.83 ms | 1.1× |
| Thor (INT8) | 1.088 ms | 4.20 ms | 3.9× |
| Thor (FP16) | 1.214 ms | 3.64 ms | 3.0× |

원인은 두 가지다.

**DX-M1** — 벤치마크의 17.99 ms는 `dxbenchmark`가 보고하는 NPU 순수 추론 시간이다. 본 문서의 75.36 ms는 DX-RT 예제가 보고하는 값으로, 그래프에 포함된 CPU 태스크(전처리 0.31 ms, 후처리 47.27 ms)와 데이터 전송이 함께 계산된다.

**Jetson** — 벤치마크는 `trtexec`가 측정한 GPU 연산 시간이다. 본 문서의 값은 파이썬 스크립트에서 측정했으며 호출 오버헤드와 스트림 동기화 대기가 포함된다. Xavier의 차이가 작은 것은 절대 연산 시간이 길어 고정 오버헤드의 비중이 상대적으로 낮기 때문이다.

두 수치 모두 유효하나 의미가 다르다. 하드웨어 성능 비교에는 벤치마크 수치를, 실제 파이프라인 구성 시 예상 성능에는 본 문서 수치를 참조한다.

### 3-2. Thor에서 FP16이 INT8보다 빠르다

파이프라인 기준으로 FP16 100.8 FPS, INT8 79.8 FPS다. `trtexec` 벤치마크에서도 같은 경향이 관찰되었다(FP16 1.214 ms, INT8 1.088 ms는 반대이나, 검출·분할 모델에서는 FP16이 일관되게 빠르다).

상세는 [results/thor.md](../results/thor.md) 4장을 참조한다.

## 4. INT8 캘리브레이션의 영향

### 4-1. 무보정 INT8은 출력이 붕괴한다

`trtexec --int8 --fp16`으로 캘리브레이션 데이터셋 없이 빌드한 엔진은 **지연 측정에는 유효하나 출력 품질이 사용 불가능한 수준이다.**

Thor에서 확인된 증상은 다음과 같다.

| 조건 | 출력 |
|---|---|
| FP16 | 정상. 거리에 따른 명확한 계조 |
| INT8 (무보정) | 화면 전체가 단일 색상에 가깝게 붕괴. 깊이 구분 불가 |
| INT8 (캘리브레이션) | FP16과 유사한 계조 회복 |

깊이 추정은 출력이 연속값이므로 활성값 범위 추정이 어긋나면 전체 출력이 좁은 구간에 압축된다. 분류·검출 모델보다 캘리브레이션에 민감하다.

**속도에는 영향이 없다.** 캘리브레이션은 빌드 시점 작업이며, 무보정 4.05 ms와 캘리브레이션 4.20 ms의 차이는 측정 편차 범위다.

### 4-2. DX-M1은 벤더 컴파일 시점에 캘리브레이션이 적용되어 있다

DX-M1의 `.dxnn` 파일은 INT8 전용이나 출력이 정상이다. 컴파일 과정에서 캘리브레이션이 수행되었음을 시사한다. 사용된 데이터셋과 방식은 공개되어 있지 않다.

### 4-3. 본 측정의 캘리브레이션 방식

| 항목 | 내용 |
|---|---|
| 알고리즘 | `IInt8EntropyCalibrator2` (TensorRT 기본) |
| 데이터셋 | 입력 영상에서 10 fps로 추출한 프레임 |
| 이미지 수 | 약 150장 |
| 전처리 | 224×224 리사이즈, ImageNet 평균·표준편차 정규화 |
| 배치 크기 | 1 |

배포 환경과 동일한 장면을 사용했으므로 대표성은 확보되나, 단일 장면이라 다양성은 제한적이다.

**주의:** 3장의 벤치마크 수치(README 3-2, 3-3의 INT8 표)는 **캘리브레이션 없이** 빌드한 엔진으로 측정한 것이다. 속도 측정에는 영향이 없으나, 해당 표의 INT8 항목은 정확도를 보장하지 않는다.

## 5. 재현 절차

### 5-1. 입력 영상 촬영

```bash
ffmpeg -y -f v4l2 -i /dev/video<N> -t 15 -c:v libx264 -pix_fmt yuv420p input_scene.mp4
```

카메라 노드 번호 확인 방법은 [setup.md](setup.md) 3-4를 참조한다.

### 5-2. Raspberry Pi 5 + DX-M1

DX-RT 예제가 영상 입출력을 지원한다.

```bash
cd dx_app/bin
./depth_anything_v2_vitb_sync \
  -m ../assets/models/depthanythingv2-vits_224x224.dxnn \
  -v <입력영상> -s --no-display --save-dir <출력_디렉토리>
```

SSH 환경에서는 `--no-display`가 필수다. 생략하면 Qt가 디스플레이 연결에 실패하여 프로세스가 종료된다.

```
qt.qpa.xcb: could not connect to display
```

### 5-3. Jetson

`trtexec`에는 영상 입출력 기능이 없다. 별도 스크립트가 필요하다.

**필요 패키지**

| 플랫폼 | 상황 |
|---|---|
| Thor | `tensorrt`, `cv2`는 시스템 파이썬에 존재. `cuda-python` 추가 설치 |
| Xavier | `tensorrt`, `cv2` 존재. `pip` 미설치이므로 `ctypes`로 CUDA 런타임 직접 호출 |

Thor에서는 시스템 패키지를 참조하는 가상환경을 사용해 호스트 환경을 변경하지 않았다.

```bash
/usr/bin/python3 -m venv --system-site-packages <venv_경로>
source <venv_경로>/bin/activate
pip install cuda-python
```

`cuda-python` 13.x에서는 모듈 경로가 `cuda.bindings.runtime`이다. 이전 버전의 `cuda.cudart`는 동작하지 않는다.

Xavier는 `pip`이 없으므로 설치 없이 처리했다.

```python
import ctypes
cu = ctypes.CDLL("libcudart.so")
```

이 방식으로 `cudaMalloc`, `cudaMemcpy`를 직접 호출하여 GPU 메모리를 관리했다.

### 5-4. 캘리브레이션 프레임 추출

```bash
ffmpeg -i input_scene.mp4 -vf fps=10 calib_frames/f%04d.jpg
```

## 6. 한계

- **정밀도가 완전히 동일하지 않다.** DX-M1은 하드웨어 고정 INT8이며 벤더 자체 양자화 방식을 사용한다. Jetson은 TensorRT의 엔트로피 기반 캘리브레이션이다. 같은 "INT8"이라도 내부 처리가 다르다.
- **캘리브레이션 데이터셋이 단일 장면이다.** 배포 환경 대표성은 있으나 일반화 성능은 확인하지 않았다.
- **정확도를 정량 평가하지 않았다.** 출력 품질은 육안 확인에 의존했다.
- **파이프라인 구현이 플랫폼마다 다르다.** DX-M1은 벤더 제공 C++ 예제, Jetson은 자체 작성 파이썬 스크립트다. 전처리·후처리 구현 차이가 처리량에 영향을 준다.
- **전처리 정규화 상수가 벤더 예제와 일치하는지 확인하지 않았다.** Jetson 스크립트는 ImageNet 표준값을 사용했다.
